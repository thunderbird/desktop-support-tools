Your address and your app password

What the Thundermail calendars add-on does with the two things you type into it.

Every line reference below is to commit 4e418b8 of thunderbird/desktop-support-tools, so they can be checked and cannot drift silently. Files are firefox-addon/manifest.json, firefox-addon/popup.html, firefox-addon/popup.js, and the shared caldav_account.js. Written 1 September 2026.

Neither value is stored anywhere. Your email address and your app password are read out of the form at the moment a request is made, held in local variables for the length of that request, and dropped. They are not written to extension storage, not synced, not put in a cookie, not put in a URL, and not logged. When the popup or sidebar closes, the page and everything in it is gone.

The requests carrying them go from your browser directly to the mail server you named. There is no backend belonging to this project for anything to be sent to.

1 Where the two values live, and for how long

Step Where
Both are read from the form only when you click a button — not on a timer, not on keystroke, not at load. popup.js:226–228 credentials()
They exist as three const locals inside that function, returned to the caller and passed straight into the request. popup.js:225–236, 245
The password is turned into an Authorization: Basic header value per request. Nothing keeps the result. popup.js:266 caldav_account.js:231–235
The only state that outlives a click is the calendar listing — the home address, the calendars found, and which is default. No credentials are in it. popup.js:63 known = { home, calendars, default }
The values in the form fields themselves live as long as the page does: until the popup loses focus, or until you close the sidebar. popup.html:22–60

There is no background script in this add-on at all, so there is no part of it that keeps running once the page is closed, and nothing that could hold a value after you have finished.

2 What is not in the code — and how to confirm it yourself

The claim is an absence, so the evidence is a search rather than a line. Run this at the top of the repository: 

$ grep -rniE "localstorage|sessionstorage|indexeddb|storage\.(local|sync|session|managed)|\
document\.cookie|console\.(log|debug|info|warn|error)|navigator\.clipboard|\
history\.(push|replace)state" firefox-addon/ caldav_account.js

firefox-addon/popup.js:276:      // No cookies, ever: this signs in with the app password you typed and

One hit, and it is a comment. No extension storage, no web storage, no IndexedDB, no cookie access, no logging of any kind, no clipboard use, and nothing written into browser history.

3 The manifest makes storage unavailable, not merely unused

A WebExtension can only call storage.local or storage.sync if it declares the storage permission. This add-on has no permissions key at all — the only permissions it names are optional host permissions, which are about which servers it may contact: 

manifest.json:26–30

  "optional_host_permissions": [
    "https://*/*",
    "http://localhost/*",
    "http://127.0.0.1/*"
  ]

So the storage APIs are not simply avoided by convention: they are not available to this add-on, and adding them would require a manifest change that is visible in review and in the permissions Firefox shows you. storage.sync matters most here — it would have put an app password on Mozilla's sync servers, which is the opposite of what an app password is for.

4 The requests themselves

Property Where
credentials: "omit" — no cookies are attached, so nothing the browser already holds for that site is sent along, and nothing is set. popup.js:278
cache: "no-store" — neither the request nor the reply enters the HTTP cache. popup.js:279
Credentials travel in a header, never in the address, so they cannot end up in history, in a referrer, or in a server's access log. popup.js:266, 272–280
A request is refused outright if its address is not the origin you granted permission for — so a reply from the server cannot redirect your password elsewhere. popup.js:254–259
Plain http:// is refused unless the server is on your own machine or network, so the password is not put on the wire unencrypted. caldav_account.js:214–228

5 Nothing is carried in the address of the page

The add-on's own pages take exactly one query parameter, ?in=sidebar, set in the manifest and used only to decide whether to offer the sidebar button (manifest.json:33, popup.js:49–58). No value you type is ever put into a URL.

6 The one piece of personal data on screen

On Thundermail, the default calendar's name is generated from the account, so it contains your email address — for example Your Thundermail Calendar (you@example.com). That name comes from the server, is shown to you, and goes no further: it is written with textContent (popup.js:312–316), never as markup, and never sent anywhere. The add-on points it out when it sees an address in a name (popup.js:347–357), because the risk is a screenshot or a paste into a public bug report rather than anything the add-on does with it.

7 What this does not claim

  • Your browser may still offer to save the password. autocomplete="off" is set on the form and on every field (popup.html:22, 29, 40, 55), but that is a request browsers are free to ignore. If you accept the offer, your browser stores it — the add-on has no part in that, and says so on screen (popup.html:93–97).
  • The password is sent to your mail server. That is the whole point: it is how the add-on signs in. "Not stored" means not kept by the add-on, not that it stays on your machine.
  • The permission you grant is remembered by Firefox until you revoke it in the Add-ons Manager. That records which server the add-on may contact — not who you are, and not your password.
  • Your own screen is not covered. An open sidebar keeps the form visible while you work, which is convenient and is also visible to anyone looking at your screen or sharing it.
